# App Template

A starting point for internal, API-driven web apps: sign-in, an app shell, server-paginated tables,
validated forms, and consistent error handling — wired together and ready to copy from.

**Stack:** React 19 · Vite · TypeScript (strict) · Tailwind 4 + daisyUI 5 ·
TanStack Router (file-based) / Query / Table v9 / Form · Axios · Zustand · Zod · Lucide

## Run it

```bash
npm install
cp .env.example .env
npm run dev            # http://localhost:5173
```

No backend yet? Set `VITE_ENABLE_MOCK=true` in `.env` and sign in with `admin` / `password`
(or `approver` / `password`). The mock lives in `src/mocks` and is loaded only when the flag is on.

Scripts: `dev` · `build` (typecheck + bundle) · `preview` · `typecheck`

## Forking this for a new project

1. Rename the app: `package.json` `name`, `VITE_APP_NAME` in `.env`, `<title>` in `index.html`, `public/favicon.svg`.
2. Point at your API: `VITE_DEV_PROXY_TARGET` (dev) and `VITE_API_BASE_URL` (prod).
3. Match the login contract in `src/features/auth/api.ts` (see **Backend contract** below).
4. Set the palette in the two `@plugin "daisyui/theme"` blocks in `src/index.css`.
5. Replace the sidebar in `src/config/navigation.ts`.
6. Delete what you don't need: `src/features/records`, the dashboard content, `src/mocks`
   (and the `enableMock` branch in `src/main.tsx`).

## Structure

```
src/
  routes/         file-based routes — the URL structure IS this folder (see below)
  routeTree.gen.ts  generated by the router plugin on every dev/build run — commit it, never hand-edit it
  router.tsx      createRouter() + the RouterContext type
  app/App.tsx     QueryClientProvider + RouterProvider + Toaster + devtools
  config/         env parsing (zod) and sidebar navigation
  lib/
    api/          axios client, typed request helpers, error normalisation, response types
    auth/         JWT helpers + route guards (requireSession, requireRoles, safeRedirect)
    queryClient.ts  global query defaults + automatic error/success toasts
  stores/         zustand: auth (persisted), theme (persisted), toasts
  hooks/          useAuth, useSessionExpiry
  components/
    layout/       AppShell (sidebar + header)
    form/         TanStack Form app hook + daisyUI field components
    table/        server-driven DataTable + URL-backed paging/sorting state
    ui/           Modal, Toaster, PageHeader, EmptyState, ErrorState, StatusBadge
  features/       one folder per feature (auth, records, …) — plain components, no route files
  mocks/          in-memory fake API
```

## Routing

Routes are files under `src/routes/`, named by URL segment. `_` prefix = pathless layout (adds a
guard or shell with no URL segment of its own); `.` in a filename = nesting (`_authenticated.records.tsx`
is `/records` nested inside the `_authenticated` layout).

```
src/routes/
  __root.tsx                    root — just the RouterContext type + <Outlet/>
  login.tsx                     /login — public, redirects away if already signed in
  _authenticated.tsx            pathless layout — beforeLoad guard + <AppShell/>
  _authenticated.index.tsx      /              (dashboard)
  _authenticated.records.tsx    /records       (search params validated here)
  _authenticated.forbidden.tsx  /forbidden
```

Each route file is thin — `validateSearch`, `beforeLoad`, and `component: SomePage` — the actual
screen lives in `src/features/*/SomePage.tsx` and is a plain component (see **Adding a feature** below).
`autoCodeSplitting` (`vite.config.ts`) splits every route into its own chunk automatically; no manual
`lazy()` or `createLazyRoute` needed.

**Adding a route:** create the file, export `Route = createFileRoute('/path')({ component: ... })`.
The dev server regenerates `routeTree.gen.ts` automatically — don't edit that file by hand. Add a link
in `src/config/navigation.ts` if it belongs in the sidebar.

**Guarding a route:** nest a file under `_authenticated` for "must be signed in." For a role-restricted
section, add a second pathless layout inside it:

```tsx
// src/routes/_authenticated._admin.tsx
import { createFileRoute } from '@tanstack/react-router'
import { requireRoles } from '@/lib/auth/guards'

export const Route = createFileRoute('/_authenticated/_admin')({
  beforeLoad: requireRoles('ADMIN'),
})
```

Then `_authenticated._admin.users.tsx` is `/users`, reachable only by an `ADMIN` user — anyone else is
redirected to `/forbidden` before the page ever renders.

**Search params as state:** `src/components/table/searchSchema.ts` defines the paging/sorting shape
shared by every list page; `useUrlPageState` wires it to `DataTable`. Extend the schema per page (see
`features/records/schema.ts`) for extra filters. This means paging, sorting and filters survive a
reload, a shared link, and the back button — there's no separate client state to keep in sync.

## Adding a feature

Copy `src/features/records` (all five files) and rename, then wire up a route file that imports the
page component:

| File | Job |
|---|---|
| `types.ts` | Shapes returned by the API |
| `schema.ts` | Zod schemas — form validation AND the route's search-param schema |
| `api.ts` | Plain functions that call the API — no React |
| `queries.ts` | Query keys plus `useQuery` / `useMutation` hooks |
| `*Page.tsx` | The screen — a plain component, not a route file |

The route file itself (`src/routes/_authenticated.<name>.tsx`) is typically 5 lines: import the page,
import the search schema if there is one, `createFileRoute(...)({ validateSearch, component })`.

## How the pieces work

**Response envelope.** Every endpoint returns `{ success, message, data, meta }`. `api.get/post/…` return
`data` directly; `api.getPage` returns `{ items, meta }` for paginated endpoints. If your envelope differs,
change `src/lib/api/types.ts` and `src/lib/api/request.ts` — nothing else knows about it.

**Errors.** The Axios interceptor converts every failure into an `ApiError` (message, status, field errors).
Spring's `IllegalArgumentException: …` prefixes are stripped so users see plain messages. Queries and
mutations toast errors automatically; pass `meta: { silent: true }` when the UI shows the error inline
(the login and create forms do). `meta: { successMessage: '…' }` toasts on success.

**Sessions.** The token and user are persisted in `localStorage`. There is no refresh token, so the JWT's
`exp` is a hard stop: `useSessionExpiry` signs the user out at that moment and the login page explains why.
A 401 from any other call does the same. Sign-out clears the query cache so one user's data never appears
for the next.

**Tables.** `DataTable` is server-driven — the backend pages and sorts, the table renders. Column ids are
sent as the `sort=` property, so they **must match backend field names**. `usePageState` produces the
`page` (0-based), `size` and `sort=field,dir` params Spring's `Pageable` expects. Changing a sort or filter
returns to page 1.

**Forms.** `useAppForm` gives typed fields that already show label, hint, error and required marker:

```tsx
const form = useAppForm({ defaultValues, validators: { onChange: schema }, onSubmit })
<form.AppField name="title">{(f) => <f.TextField label="Title" required />}</form.AppField>
<form.AppForm><form.SubmitButton>Save changes</form.SubmitButton></form.AppForm>
```

Errors appear after a field is touched or a submit is attempted. Add new field types in
`components/form/fields.tsx` and register them in `form.ts`.

**Roles.** Roles are normalised to upper case without `ROLE_`. Use `useAuth().hasAnyRole('ADMIN')` for
conditional UI, `roles` on a nav item to hide a link, and `requireRoles('ADMIN')` in a route's
`beforeLoad` (see **Routing** above) to guard a whole section. Hiding UI is a convenience only — the
API must enforce permissions.

**Why an effect in `AppShell`, not just `beforeLoad`.** `beforeLoad` only runs on navigation, so it
can't react to a session that ends while the user is already sitting on a page (token expiry mid-session,
a 401 from some other tab's request). `AppShell` has a small effect for that case. It intentionally
reads `router.state.location.href` *inside* the effect rather than subscribing to it reactively — doing
the latter (or rendering a `<Navigate search={{...}} />` with a fresh object each render) causes the
redirect to re-fire on the navigation it just caused, nesting `redirect=` inside itself until React
throws "Maximum update depth exceeded." If you touch this effect, keep that in mind.

## Backend contract

Assumptions to confirm against your API (designed for a Spring Boot backend):

- **Login:** `POST /auth/login` with `{ userName, password }` returning
  `{ accessToken, user: { id, userName, roles: string[] } }` inside the envelope. If yours returns only a
  token, decode the claims in `toSession` (`src/features/auth/api.ts`, helper in `lib/auth/jwt.ts`).
- **Token:** a JWT with an `exp` claim. Without `exp` the client can't sign out early; it falls back to the
  first 401.
- **Errors:** JSON `{ timestamp, status, error, message }`. An optional `errors: { field: message }` object
  is shown against form fields.
- **Paging:** `page` (0-based), `size`, `sort=property,asc|desc`; response `meta` has
  `page, size, totalElements, totalPages, hasNext, hasPrevious`.
- **Dates:** ISO-8601 strings.
- **CORS:** in dev the Vite proxy makes requests same-origin, so none is needed. In production allow your
  frontend origin on the API.

## Choices worth knowing

- **TanStack Table v9** is a rewrite of v8: `useTable` with explicit `tableFeatures`, not `useReactTable`.
  Registered features live in `components/table/tableFeatures.ts`. Add filtering, selection or visibility
  there when a table needs them.
- **TanStack Router plugin order matters.** In `vite.config.ts`, `tanstackRouter(...)` MUST come before
  `react()` — reversed, route generation and code splitting fail silently with no error.
- **`routeTree.gen.ts` is generated, not hand-written** — regenerated automatically by `npm run dev` /
  `npm run build`. Commit it (it's real source the app imports at runtime); never edit it directly.
- **Fonts** are bundled (IBM Plex Sans via `@fontsource-variable`), so the app makes no third-party requests.
- **daisyUI built-in themes are disabled**; only `app-light` and `app-dark` are generated, keeping CSS small.
